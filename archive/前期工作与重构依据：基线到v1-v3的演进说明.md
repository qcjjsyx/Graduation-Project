# 前期工作与重构依据：基线到 v1 / v2 / v3 的演进说明

最后更新：2026-08-26  
文档性质：历史工作量说明、问题发现记录和彻底重构的依据  
当前状态：归档文档，不作为当前实现规范

## 1. 文档目的

本项目不是从一开始就按照当前的软硬件边界设计的。早期实现先围绕“固定点多前沿稀疏 LU 求解器”建立了一套能够运行的代码、SystemC 系统模型和若干 RTL 原型；随后又以 v1、v2、v3 三个独立快照，对缩放、Tile BFP 和定点精度进行了连续实验。

这些工作形成了重要的前期基础，但也逐渐暴露出一个事实：当时的主要优化目标是让一条已经绑定 INT32/定点格式的路径在若干测试矩阵上得到可接受结果，而不是先把算法、硬件计算资源、SystemC 模型和软硬件接口分层。因此，后续继续在原路径上堆叠格式、scale、rescue 和 task 字段，难以在有限时间内同时得到清晰的架构结论和可信的硬件验证结果。

本文回答四个问题：

1. 原始基线代码已经完成了什么；
2. 基线暴露了哪些算法、数值、建模和工程问题；
3. v1、v2、v3分别修改了什么、解决了什么、又留下了什么；
4. 为什么当前项目需要从“固定点整树路径”重构为“可替换计算后端 + 指令/描述符接口 + SystemC主硬件模型”的架构。

本文只记录演进过程，不重新定义当前架构。当前架构以仓库根目录的[项目总体架构重新定型方案](../项目总体架构重新定型方案.md)和新的[项目范围与交付边界](../docs/architecture/项目范围与交付边界.md)为准。

## 2. 版本关系和总体结论

| 阶段 | 主要目标 | 主要产物 | 取得的结论 |
|---|---|---|---|
| 原始基线 | 建立多前沿稀疏 LU 的软硬件流程 | 软件符号分析、定点 artifact、SystemC 系统模型、ATU/HPU/GCU 等 RTL 原型 | 证明了任务、消去树、前沿装配、主元映射和定点节点计算可以串起来；也暴露了数值与接口耦合问题 |
| v1 | 解决共享 exponent 带来的动态范围问题 | 2 的幂次行缩放、行列缩放、Ruiz 缩放实验 | 缩放可以改善部分矩阵，但没有一个静态缩放策略在所有指标上占优，也没有改变整棵树依赖全局定点格式的事实 |
| v2 | 细化缩放粒度，避免一个 node exponent 覆盖整个 front | 16×16 Tile BFP、tile exponent、QAU 两阶段装配、U/update 独立 exponent | 局部 scale 比全 front scale 更合理，但元数据、装配、求解和控制复杂度明显上升，且大量节点仍需 FP64 rescue |
| v3 | 降低 v2 的 rescue 数量并改善 L 乘子精度 | QF26、F20→F26 重算实验、precision state 和重算周期模型 | 统一 QF26优于逐节点自适应重算，但仍未形成可独立工作的纯整数硬件路径 |
| 当前重构 | 重新划定软硬件责任和可交付范围 | FP64 golden、FP32 SystemC、局部 INT32 GEMM 行为模型、command/descriptor 接口 | 将数值参考、硬件架构模型和未来 RTL 后端解耦，使 SystemC 能先承担真实的硬件执行模型 |

需要特别说明：v1、v2、v3是软件/SystemC实验分支或独立快照，不等价于三代已经完成的 FPGA/ASIC 硬件。每一版都修改了软件 artifact、SystemC 数值路径和控制/报告逻辑，但没有形成一个包含真实 GEMM RTL、完整 GCU、完整 Panel-LU、TRSM 和求解器的闭环硬件版本。

## 3. 原始基线代码做了什么

### 3.1 软件侧：从稀疏矩阵生成节点任务和存储制品

基线软件负责把输入稀疏方阵转换为多前沿执行所需的数据和任务，主要流程是：

```text
稀疏矩阵 A、RHS b
  → 重排与符号分析
  → fill-in 估计、消去树、超节点/前沿划分
  → map table、节点数据、子节点更新地址
  → 定点量化和 exponent 元数据
  → NodeTask 队列 + DDR memory image
```

它已经涉及了多前沿实现中最重要的结构性工作：节点依赖关系、父子更新关系、前沿矩阵布局、P-vector/映射表、任务顺序、DDR 地址以及 L/U/update 的写回位置。软件还负责生成验证用的原始矩阵、RHS 和参考解，以便计算 residual、后向误差和解误差。

早期软件曾经把“输入矩阵的数值结构必须对称”作为隐含前提。这对一般非对称稀疏矩阵是不成立的。后续已经改为：数值矩阵仍保留原始的非对称 A，符号分析使用 `pattern(A) ∪ pattern(Aᵀ)` 构造安全包络。这个修正保持了数值问题和结构问题的区分，也是一次重要的问题发现。

### 3.2 SystemC：对系统控制和节点执行过程做功能/事务建模

基线 SystemC 不是简单的一个 C++ 求解器，而是已经搭出了相当完整的系统外壳。当前代码中可以看到以下硬件风格模块：

- Task Fetch：从任务存储中获取节点任务；
- Dependency Scoreboard：维护子节点完成数和父节点就绪状态；
- Buffer Manager：管理片上前沿/工作区 buffer；
- Front Assembler：从 DDR 和子节点 update 形成当前 front；
- HPU：收集候选并选择主元；
- ATU：维护逻辑行到物理行的 P-vector，支持无搬移行交换；
- Kernel Dispatcher：发射 FACT、TRSM、GEMM-Schur 等操作；
- Result Writer：写回 L/U/P/update；
- Completion Monitor：结束检测和状态报告；
- DDR、FIFO、clock、ready/valid 和事务延迟模型。

因此，基线已经完成了“软件制品驱动设备执行”的基本链路，而不是只有孤立的数值函数。它可以输出 timeline、operation、memory、node 和 summary 等报告，能够观察依赖、buffer、DDR 事务和节点完成过程。

### 3.3 基线的数值执行方式

基线定点路径采用以下思路：每个节点的输入 front 用 `int32 mantissa + exponent` 表示，QAU 将本地贡献和子节点 update 对齐到共同的装配尺度，再使用较宽 accumulator 累加并重新量化。节点内部执行：

1. HPU 在候选行中选择绝对值最大的主元；
2. ATU 更新 P-vector 而不是搬移整行数据；
3. 计算 L 乘子；
4. 执行 Panel LU、TRSM 和 Schur update；
5. 将 L/U/P/update 写回 DDR，供父节点继续装配。

除了定点路径，SystemC 还保留了 FP64 参考路径和 precision rescue 路径。实际代码中，部分 front 装配和数值核会直接调用 `SystemMemory` 中的 C++ 容器和普通 C++ 数值函数；最终树形求解也曾在 SystemC 仿真结束后由普通 C++ `solve_fp64` 或 `solve_fixed` 完成。

这说明基线 SystemC 的准确定位应是：

> 已具备硬件控制、事务和数据流外壳的系统级行为模型；数值运算部分仍是 C++ 行为核与周期估算的混合实现，不是完整 RTL 等价模型。

它已经足以验证任务依赖、内存布局、主元映射和端到端功能，但不能据此宣称“硬件已经真实执行了每个乘加、除法、写回和求解周期”。

### 3.4 RTL 原型做了什么

基线 RTL 主要完成了模块级原型，而非顶层设备：

- ATU：同步的 P-vector 初始化、查询和 swap 原型；
- HPU：候选比较树和最大绝对值归约原型；
- GCU 子模块：任务获取、依赖记分牌、buffer 管理和 micro-scheduler 的部分状态机；
- GCU top：仍未形成完整的可运行系统顶层；
- Matrix Engine/GEMM：没有可用于当前联调的 INT32 GEMM RTL。

早期文档曾把 SFU、Tensor Core、DMA、Scatter Engine 和完整 GCU 描述成目标架构，但其中相当一部分停留在设计说明、接口预留或占位状态，不能视为已经完成的硬件实现。

## 4. 原始基线暴露的问题

### 4.1 算法范围没有先冻结

项目最初同时使用了“稀疏矩阵求逆”“多 RHS 求解”“对称/非对称矩阵”“LU 主元交换”“硬件加速”几个不同层次的目标。若直接实现显式逆矩阵，代价和验证复杂度都会显著上升；真正适合作为首版交付的是 `Ax=b`，显式逆只能作为多 RHS 扩展。

此外，当前结构只在符号层面能够通过转置闭包支持一般非对称模式；数值层面的动态主元、延迟主元、结构动态扩展和不规则 front 并没有全部实现。因此“支持非对称稀疏方阵”不能简单等同于“已经完成通用非对称稀疏 LU”。

### 4.2 INT32 被当成了整棵算法的数值前提

原路径把输入、front 装配、Panel-LU、TRSM、Schur update、L/U/update 写回和向量求解都拉进了固定点/整数格式体系。这样做的直接结果是：每一次树节点更新都可能改变后继节点的 exponent、可表示范围和有效精度，软件量化策略和硬件 QAU/GCU 控制强耦合。

对于病态矩阵，这不是简单增加位宽就能解决的问题。基线实验观察到：

- 576JJ 存在约 `4.1699e-7` 的极小主元；FP64 默认阈值会报告 numeric failure，定点路径则出现严重精度损失；
- 1024JJ 在节点内连续整数消元后，原本非零的剩余候选被舍入为零，HPU 得到 zero pivot；
- 小 residual 不一定对应小前向解误差，例如 256JJ 的 fixed residual 约为 `5.377e-4`，解误差仍约为 `2.904`。

这表明问题包含动态范围、消去过程中的 cancellation、主元策略、L/U 表示范围和病态性放大，不能全部归因于“矩阵乘法位数不够”。

### 4.3 SystemC 的控制粒度和数值粒度不一致

SystemC 在控制侧已经表现为 FIFO、状态机、依赖和 DDR 事务，但数值侧仍经常通过普通 C++ 容器直接读取/写入全局内存，并以一个函数调用完成整个 Panel 或 GEMM 的计算。其周期通常来自预设的吞吐估计，而不是由每个真实算子状态推进出来。

这会导致两个问题：

- 可以证明算法和控制流“能完成”，但不能证明未来 RTL 端口、buffer 生命周期和反压行为能够逐事务替换；
- 量化、rescue 和 solve 有时在硬件路径外完成，导致报告中的“硬件周期”和实际计算路径之间存在语义差距。

### 4.4 NodeTask 把软件内部产物暴露成了硬件协议

早期 `NodeTask` 同时携带 front 尺寸、pivot 尺寸、DDR 地址、父节点地址、map table 地址、L/U 地址等字段。字段本身并不是错误，但它把软件当前的节点划分和存储布局直接固化成硬件读取协议。

只要软件改变超节点划分、tile scale、update 组织、求精策略或任务调度，就可能需要修改硬件字段、解码器和控制状态机。这正是“软件优化导致硬件也必须跟着改”的根本来源。

### 4.5 工程范围超过了当时的可交付能力

早期目标隐含要求同时完成：完整 GCU、DMA、buffer、ATU、HPU、Panel-LU、TRSM、INT32 GEMM、QAU、树形求解、Verilog 联调、SystemC 仿真和多矩阵实验。实际 RTL 中 GCU top 仍为空或为占位逻辑，micro-scheduler 的部分操作也没有完整实现；而真正的 INT32 GEMM RTL并不存在。

因此继续以“完整硬件代码全部落地”为唯一交付标准，会把大量时间消耗在接口拼接和量化控制上，反而无法形成可信的核心实验。

## 5. v1：用缩放缓解共享 exponent 的动态范围问题

### 5.1 v1要解决的问题

基线每个节点使用较粗的共享尺度。一个极大元素会抬高 scale，导致大量较小元素在装配或消元时丢失有效位；一个极小元素又可能造成溢出、饱和或不稳定的中间结果。v1因此没有先更换整个格式，而是验证低硬件代价的 2 的幂次缩放能否改善动态范围。

### 5.2 v1做的改动

v1是独立优化快照，没有修改根目录基线，主要比较了：

- B0：只有行缩放；
- B1：交替行列满归一化；
- B2：幂次 Ruiz 行列缩放。

缩放因子限制为 2 的整数次幂，因此可以主要通过修改 exponent 完成，不需要通用乘法器。v1还增加了列缩放的保存和解坐标恢复，使输出、residual、后向误差和解误差回到原始坐标。

### 5.3 v1得到的证据

典型结果如下：

| 矩阵 | 方案 | 原方程 residual | 解误差 | Rescue | 迭代求精 |
|---|---|---:|---:|---:|---:|
| 576 | B0 row | `2.346e-2` | `2.362` | 13 | 0 |
| 576 | B1 row-column | `4.593e-3` | `0.958` | 13 | 2 |
| 576 | B2 Ruiz | `1.120e-2` | `2.914` | 12 | 5 |
| 1024 | B0 row | `9.434e-4` | `1.394e-3` | 1 | 40 |
| 1024 | B1 row-column | `9.730e-4` | `1.436e-3` | 1 | 39 |
| 1024 | B2 Ruiz | `3.916e-4` | `9.094e-3` | 1 | 1 |

576JJ 上 B1 相对 B0 将 residual 改善约 80.4%，说明列方向动态范围确实是重要因素；1024JJ 上 B2 大幅减少了迭代求精轮数，但前向解误差反而变差。v1因此证明了：缩放有效，但 residual、解误差和周期可能朝不同方向变化。

### 5.4 v1没有解决的问题

- 没有一个静态缩放策略对所有矩阵和所有指标都占优；
- 仍然是整棵树共享定点/INT32 计算边界；
- 没有解决小主元、零主元和 L/U 表示范围问题；
- 没有解决 SystemC 数值函数绕过显式硬件 buffer 的问题；
- 没有补齐真实 GEMM RTL 和 GCU 顶层。

因此 v1是一次有价值的数值预处理实验，但不是硬件架构的根本修复。

## 6. v2：从 node 级共享 scale 改为 16×16 Tile BFP

### 6.1 v2要解决的问题

v1仍以较大的 front/node 为尺度。对于一个内部数值差异很大的 front，即使行列缩放后，一个 exponent 仍可能被少数极端元素决定，造成其余区域有效位不足。v2把目标改为：让 scale 至少在局部 tile 内表达。

### 6.2 v2做的改动

v2引入 16×16 Tile BFP：每个 tile 使用独立 exponent，mantissa 仍采用 int32。相应改动覆盖了完整制品链路：

- 软件写入 tile exponent 和 tile 数据；
- DDR memory image 携带 tile 元数据；
- QAU 按目标 tile 进行两阶段对齐、累加和再量化；
- HPU 比较候选时按实际 tile exponent 还原数值；
- L 使用 QF 格式，U/update 使用 tile exponent；
- 父节点按 tile 映射接收子节点 update；
- 节点增加局部因子检查，失败时进入 FP64 rescue。

### 6.3 v2得到的证据

相对于 v1/基线的粗粒度 scale，v2在三组矩阵上均能得到低于 `1e-3` 的 final residual，但 rescue 数量非常高：

| 矩阵 | residual | 解误差 | FP64 Rescue |
|---|---:|---:|---:|
| 256 | `5.964e-4` | `1.514` | 68 / 73 |
| 576 | `3.252e-4` | `6.934` | 150 / 157 |
| 1024 | `1.012e-4` | `3.000e-8` | 122 / 274 |

这说明 tile scale 确实能够改善某些局部动态范围，但不能据此得出“整数矩阵核已经能够独立完成大部分分解”的结论。尤其是 576JJ，绝大多数节点仍走了高精度 rescue。

### 6.4 v2引入的新代价和未解决问题

- 每个 tile 都需要 exponent 及其地址/布局语义；
- QAU 不再是简单的统一移位，而是包含目标 tile 选择、对齐、累加、再量化和溢出处理；
- HPU、Panel-LU、U/update 写回和父子 update 装配都必须理解 tile scale；
- 向量求解仍不是完整纯整数 V-format 路径；
- rescue 依旧使用高精度行为路径，不能作为 RTL 已实现能力；
- ABI、NodeTask、SystemC 控制逻辑随着数值格式变复杂，进一步放大了接口耦合。

所以 v2的主要价值是把“全 front scale 太粗”这个问题验证清楚，同时也证明了：如果把整棵树都绑定到 Tile BFP，硬件控制复杂度会快速增长。

## 7. v3：提高 L 乘子精度并评估自适应重算

### 7.1 v3要解决的问题

v2默认 L 采用 QF20，量化步长约为 `2^-20 = 9.54e-7`，而局部因子检查门槛约为 `2e-7`。这意味着很多节点即使没有明显的零主元、溢出或饱和，也可能仅因 L 乘子精度不足而进入 FP64 rescue。

### 7.2 v3做的改动

v3在不改变 v2 Tile BFP 格式和大部分 ABI 的前提下，比较了：

- 统一 QF26；
- 失败节点从 F20 重算到 F26，再决定是否 FP64 rescue。

它还增加了节点级精度状态，例如实际 `l_frac_bits`、是否尝试重算、是否 precision-assisted 以及是否最终 rescue，并将重算计入周期模型。

### 7.3 v3得到的证据

统一 QF26 相对于 v2 QF20 的结果为：

| 矩阵 | residual：v2 → v3 | 解误差：v2 → v3 | Rescue：v2 → v3 | 周期变化 |
|---|---:|---:|---:|---:|
| 256 | `5.964e-4 → 7.096e-5` | `1.514 → 0.174` | `68 → 9` | `+0.69%` |
| 576 | `3.252e-4 → 3.024e-4` | `6.934 → 0.554` | `150 → 37` | `-0.43%` |
| 1024 | `1.012e-4 → 2.816e-5` | `3.000e-8 → 1.293e-6` | `122 → 49` | `-17.02%` |

统一 QF26在这组三个矩阵上优于逐节点 F20→F26 重算：自适应方案需要重复执行大量定点分解，只有 1024 少量减少 rescue，三组的 residual、解误差或周期也没有形成稳定优势。因此 v3给出了一个清晰的实验结论：对于当时的 Tile BFP 路径，固定 QF26 比运行时复杂的两级精度重算更适合作为实验默认值。

### 7.4 v3没有解决的问题

- QF26仍然是整条定点节点路径的一部分，INT32 的表示范围更窄，仍需溢出和失败处理；
- rescue 仍然是 SystemC/C++ 高精度路径，没有对应 RTL；
- 向量求解仍没有变成与定点因子完全一致的纯整数硬件流程；
- 局部因子检查使用了高精度行为判定，难以直接映射到首版可综合硬件；
- Tile BFP 的 exponent 元数据和 NodeTask/ABI 复杂度仍然存在；
- 没有真实 INT32 GEMM RTL，无法完成真正的 RTL-SystemC GEMM 联调。

因此 v3优化了数值结果，却进一步证明了：继续在“整棵树固定点化”的方向上推进，会不断把研究重点转移到量化格式和异常控制，而不是 LU、TRSM、GEMM 的可复用硬件架构。

## 8. 从基线到 v3 的总体问题归纳

### 8.1 数值问题

固定点路径的主要风险不是一个参数，而是多个环节叠加：输入量化、front 装配、子节点 update 对齐、Panel 消元、L 乘子量化、U/update 写回、主元比较和向量求解都会传播误差。v1到 v3分别改变了缩放粒度和 L 精度，但实验仍需要 rescue、迭代求精和高精度 shadow/reference。

### 8.2 架构问题

GEMM 是适合矩阵阵列加速的吞吐型算子；Panel-LU、动态主元和 TRSM 是依赖密集、包含比较/除法/行交换的控制型算子；树形求解又更偏向不规则访存和向量操作。把这三类工作强行放进同一套 INT32 矩阵乘格式，并不会自动得到统一而简单的硬件架构。

### 8.3 模型问题

SystemC 已经有系统级硬件外壳，但当前数值核、solve、rescue 和 memory 之间仍有混合边界。若不继续改造，SystemC 只能证明“软件结果可以在仿真流程中产生”，不能证明“未来硬件按照 command、buffer、latency 和 backpressure 执行了这些操作”。

### 8.4 接口问题

NodeTask 字段越来越多地表达软件当前的数据结构，而不是表达硬件应该执行的动作。v2/v3又需要增加 tile exponent、U/update exponent、QF、retry 和 rescue flags，使接口与某一版数值格式绑定得更紧。

### 8.5 交付问题

当前没有 INT32 GEMM RTL，GCU top 和完整 Matrix Engine 也没有闭环。若把“所有硬件模块真实 Verilog 实现并联调”作为唯一成果，六个月内难以同时完成可靠的架构验证、数值验证和论文实验。

## 9. 为什么必须进行彻底重构

### 9.1 把 INT32 限制收缩到真正需要它的边界

INT32 是当前 GEMM 单元的接口能力，不应自动成为稀疏 LU 算法、主元选择、TRSM、向量求解和整个消去树的全局数值法律。新的思路是：

```text
FP32 front/tile
  → GEMM 调用边界量化
  → INT32 GEMM 行为模型或未来 RTL
  → 反量化
  → FP32 后续控制与装配
```

这样只需要在矩阵乘法调用处管理 scale、overflow、saturation 和累加宽度，不再让每个树节点的 scale 传播为整棵树的 ABI 和调度问题。

### 9.2 让 SystemC 真正成为硬件架构模型

新的 SystemC 主线应保留基线已经验证过的 GCU、依赖、DDR、buffer、HPU、ATU 和报告框架，但把数值算子改为显式 request/response 和 buffer 驱动：

- Panel-LU 体现主元选择、swap、除法/倒数、更新和写回状态；
- TRSM 体现 tile 读取、依赖、计算延迟和输出；
- GEMM 体现 tile 量化、INT32 乘加、宽 accumulator、反量化、反压和写回；
- solve 作为明确的 `SOLVE_FORWARD` / `SOLVE_BACKWARD` command 完成闭环；
- 普通 C++ FP64 函数只作为 golden/checker，不直接替设备路径写结果。

在没有 INT32 GEMM RTL 时，`Int32GemmBehavioral` 是合理的硬件替身：它模拟未来 GEMM RTL 的事务接口、tile 延迟、累加、溢出和写回行为。将来拿到真实 RTL 后，只需替换 GEMM backend，而不必重新设计 GCU、front 流程和软件协议。

### 9.3 将软件/硬件交互物从字段改为指令

当前重构把长期接口改为 command stream + descriptor table：软件负责生成节点描述符、依赖 token、buffer descriptor 和操作序列；硬件负责解析 command、等待依赖、申请资源、执行操作和报告完成/错误。

这并不是删除所有元数据，而是把“数据描述”与“执行动作”分开：

```text
Command: 做什么、依赖谁、使用哪个 descriptor
Descriptor: 数据在哪里、尺寸多大、stride/scale/布局是什么
Status: 完成、失败、overflow、pivot、stall、cycles
```

这样软件可以改变重排、超节点、tile 划分和任务生成策略，而不必为每次算法调整重写 GCU 的字段解码逻辑。

### 9.4 明确求解阶段的交付边界

首版不需要把树形前代/回代全部做成独立 Verilog IP。求解阶段仍应在 SystemC 中完成真实的前代、回代、P-vector 语义和写回数据消费，作为可执行硬件架构模型；RTL 首版聚焦可验证的 GCU、HPU、ATU、buffer/协议和必要的计算接口。

这保留了“分解和求解是一条完整流程”的系统价值，同时避免把不规则向量求解、动态主元和矩阵阵列 RTL 一次性全部实现。

### 9.5 将交付分为三种可信度不同的后端

当前重构采用三种后端，分别回答不同问题：

| 后端 | 作用 | 是否作为硬件周期结论 |
|---|---|---|
| FP64 C++ golden | 数学参考、正确性 checker、病态矩阵基准 | 否 |
| FP32 SystemC | 主要硬件架构模型，验证控制、buffer、命令、延迟和端到端流程 | 是，作为架构级周期/事务结论 |
| FP32 + INT32 GEMM SystemC | 在 GEMM 边界验证量化和整数矩阵核适配 | 是，限定为行为级 GEMM 模型 |

这比让一个固定点 SystemC 路径同时充当 golden、硬件模型和量化验证器更容易解释，也更容易在六个月内形成可复现实验。

## 10. 前期工作量应如何表述

前期工作不应表述为“之前的代码全部无效”。更准确的表述是：

1. 完成了从稀疏矩阵到消去树、超节点、front、map table、任务和 DDR artifact 的软件链路；
2. 搭建了包含任务获取、依赖记分牌、buffer、DDR、装配、HPU、ATU、写回和报告的 SystemC 系统骨架；
3. 完成了固定点 Panel-LU、TRSM、Schur update、向量求解、precision rescue 和迭代求精的行为验证；
4. 完成了 ATU、HPU、GCU 部分子模块的 RTL 原型和测试；
5. 通过 v1 验证行列缩放、通过 v2 验证 tile 级 scale、通过 v3 验证 QF26 与自适应重算；
6. 在真实矩阵上记录了 residual、解误差、rescue、迭代次数和周期之间的矛盾；
7. 由此发现了原方案的边界：量化边界过早、接口过度字段化、SystemC 数值与硬件执行粒度不一致、RTL 计算核缺失。

因此，彻底重构不是简单推倒重来，而是把前期实现从“可运行的探索性原型”提升为“分层、可替换、可验证的系统架构”。前期 v1/v2/v3 的实验结果仍作为历史对照，用来解释为什么当前不再把全树 INT32/Tile BFP 作为主线。

## 11. 当前重构的验收边界

当前项目不再要求在第一阶段完成所有模块的流片级 RTL，而要求形成以下闭环：

```text
输入稀疏矩阵
  → 软件符号分析/重排/消去树/超节点
  → command stream + descriptor + memory image
  → SystemC GCU/依赖/buffer/DDR
  → Panel-LU + HPU/ATU + TRSM
  → GEMM 行为模型（必要时局部 INT32 量化）
  → L/U/P/update 写回
  → SystemC SOLVE_FORWARD/SOLVE_BACKWARD
  → FP64 golden checker、residual、后向误差、解误差和周期报告
```

RTL 作为关键模块的可综合原型和协议验证载体逐步接入。没有真实 GEMM RTL 时，报告必须明确标注 `SYSTEMC_INT32_GEMM_MODEL`，不能伪装成 `RTL_GEMM` 结果。

## 12. 结论

原始基线解决了“如何把多前沿稀疏 LU 的软件结构、任务依赖、前沿数据、主元映射和定点节点计算串成一条可运行流程”的问题。v1、v2、v3则逐步回答了“全树定点路径的动态范围、缩放粒度和 L 精度是否可以通过局部改进修复”的问题。

实验结论并不是原工作失败，而是边界越来越清楚：缩放能缓解问题，Tile BFP 能细化问题，QF26 能减少部分 rescue，但这些优化无法替代清晰的硬件计算边界、可执行的 SystemC 设备模型、可替换的 GEMM 后端和稳定的指令接口。

所以当前的彻底重构有明确依据：保留已经验证的多前沿控制骨架和模块思想，放弃把 INT32/定点格式扩散到整棵树的做法，把 FP64 用作基准、FP32 用作主要 SystemC 硬件模型，只在 GEMM 边界适配 INT32，并用 command/descriptor 取代对软件内部字段的强绑定。这样才能在剩余周期内完成一个可解释、可验证、可继续演进的项目。
