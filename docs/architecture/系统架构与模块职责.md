# 系统架构与模块职责

状态：当前主线文档

## 1. 总体结构

```text
输入矩阵 A、RHS b
        │
        ▼
软件求解编译器
  ├─ 均衡与数值策略
  ├─ pattern(A) ∪ pattern(Aᵀ)
  ├─ ordering / fill / elimination forest
  ├─ supernode / front / local map
  ├─ descriptor table
  └─ command ring + data image
        │ command / descriptor / data
        ▼
设备执行器（SystemC 或 RTL）
  ├─ Command Fetch
  ├─ GCU / Dependency Scoreboard
  ├─ DMA / Buffer Manager / Front SRAM
  ├─ Assembly / Extend-Add
  ├─ Panel-LU ───── HPU
  │       └─────── ATU
  ├─ TRSM
  ├─ GEMM-Schur ── Precision Adapter ── INT32 GEMM backend
  ├─ Factor/Update Writer
  └─ Solve Controller / TRSM
        │ DDR snapshot / completion
        ▼
独立 FP64 checker 与实验报告
```

## 2. 软件侧模块

### 2.1 Input and normalization

读取稀疏方阵和 RHS，保留原始数值矩阵，不把非对称矩阵数值对称化。可以执行结构不变的二的幂行均衡，但必须记录缩放 exponent 并按原方程验证结果。

### 2.2 Symbolic compiler

负责：

- 构造对称符号包络；
- ordering；
- fill 和 elimination forest；
- supernode、front 和 update 区域；
- local row/column map；
- front 上限和 buffer 需求检查。

该模块不下沉到硬件。硬件只接收已经编译好的结构产物。

### 2.3 Command compiler

将软件内部的 node compiler IR、消除树和 front 描述转换为：

- command ring；
- descriptor table；
- data image；
- completion 预期和依赖 token。

历史 `NodeTask` 已归档；当前软件内部使用不带设备二进制布局的 node compiler IR。

## 3. 设备侧模块

### 3.1 Command Fetch

从 command ring 读取固定格式命令，检查版本、长度、ID 和 descriptor 引用，生成非法命令状态。

### 3.2 GCU

GCU 是命令执行器，不负责 ordering、fill 或 supernode 构造。职责包括：

- command decode；
- dependency token 管理；
- buffer 和资源分配；
- Panel、TRSM、GEMM、DMA 的发射；
- timeout、abort 和 completion；
- cycle、bytes、pivot、overflow 和 retry 统计。

### 3.3 Buffer/DMA/Assembly

- 将 DDR 中的 contribution、front 和 descriptor 搬入片上 buffer；
- 管理 front、update、factor 和 scratchpad 生命周期；
- 执行 extend-add；
- 将结果按 descriptor 写回 DDR；
- 将满/空、端口冲突和反压传递给 GCU。

Assembly 可以使用 C++ 容器实现 buffer，但不能直接绕过 DDR/descriptor 从黄金对象读取结果。

### 3.4 HPU

输入是当前列的候选值和逻辑行号，输出确定性的 pivot 行、pivot 值和状态。首版使用最大绝对值归约和固定 tie-break，不同时实现 CALU、阈值搜索和复杂 tournament 分支。

### 3.5 ATU

维护 logical row 到 physical row 的 P-vector。pivot 行交换只交换 P-vector 项，计算核的所有访问都通过同一映射语义进行查询。

### 3.6 Panel-LU

在 SystemC 中实现显式的 load、pivot、swap、reciprocal/divide、update 和 writeback 状态，使用 FP32/FP64 行为运算，并对每个状态配置资源数量和延迟。

### 3.7 TRSM

支持两类分解内操作：

- `TRSM_LEFT_LOWER`：计算 `U12 = L11⁻¹(PF12)`；
- `TRSM_RIGHT_UPPER`：计算 `L21 = F21U11⁻¹`。

最终 solve 复用相同的三角求解语义，在 SystemC 中完成树形前代和回代。RTL solve 不是首版必要条件。

### 3.8 GEMM-Schur

计算：

```text
F22 ← F22 − L21 × U12
```

SystemC 默认可以使用 FP32/FP64 GEMM 行为模型。若使用 INT32 GEMM 后端，量化和反量化只发生在该次 GEMM 的 tile 边界。

### 3.9 Solve Controller

根据已经写回并提交的 L/U/P 和 RHS 执行树形前代、回代。单 RHS 的求解依赖强、计算量相对小，因此首版主要在 SystemC/Host 完成，避免为了完整性新增复杂 RTL 向量核。

## 4. 数据和控制原则

### 4.1 控制与数据解耦

命令表达“做什么”，descriptor 表达“对哪一块数据、以什么尺寸和布局做”。GCU 不读取软件内部的消除树字段。

### 4.2 数值与控制解耦

数值误差不会改变结构依赖。若量化导致 pivot 不稳定，设备返回数值状态，由软件选择重试或报告不支持；不能通过改变 token 语义掩盖失败。

### 4.3 设备路径与黄金路径解耦

所有设备算子只能消费 DDR/descriptor/buffer；FP64 reference 只能在设备输出之后进行检查。

## 5. 推荐运行模式

```text
FP64_GOLDEN
    数学参考，不模拟设备

FP32_SYSTEMC
    浮点数值 + SystemC 硬件数据流/周期

FP32_SYSTEMC_INT32_GEMM
    浮点系统 + 局部量化 + SystemC INT32 GEMM 行为模型
```

未来获得 Verilog GEMM 后，用同一 transaction 接口替换最后一种模式中的 GEMM backend。
