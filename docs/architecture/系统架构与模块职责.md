# 系统架构与模块职责

状态：当前主线文档

## 1. 总体结构

默认主元策略是「软件数值预处理 + 硬件固定主元顺序」（STATIC）；HPU/ATU 只服务可选的
DYNAMIC_PANEL 策略。推进顺序先完成 STATIC 数值核及分解—求解闭环，再开展 T14
HPU/ATU 契约统一和动态路径接入；T14 不再作为 STATIC 阶段的硬前置，按新编号执行，原有交付要求保留。

```text
输入矩阵 A、RHS b
        │
        ▼
软件求解编译器
  ├─ 数值预处理（二的幂行均衡 + 全局 max-product 行匹配）
  ├─ pattern(B) ∪ pattern(Bᵀ)
  ├─ ordering / fill / elimination forest
  ├─ supernode / front / local map
  ├─ descriptor table
  └─ command ring + data image
        │ command / descriptor / data
        ▼
设备执行器（SystemC 或 RTL）
  ├─ Command Fetch
  ├─ GCU / Dependency Scoreboard
  ├─ DMA / Buffer Manager / Front SRAM
  ├─ Assembly / Extend-Add
  ├─ 全 front 扫描 / 固定尺度归约
  ├─ Panel / TRSM / GEMM command controllers
  │    └─ Tile task generator / scoreboard / dispatcher
  │         └─ 共享多模式 PE 池（16×16 tile）
  ├─ HPU / ATU（仅后续 DYNAMIC_PANEL）
  ├─ Precision Adapter / INT32 GEMM backend（后续）
  ├─ Factor/Update Writer
  └─ Solve Controller / TRSM
        │ DDR snapshot / completion
        ▼
独立 FP64 checker（对原始 A x = b）与实验报告
```

以上为目标架构，2026-09-28 的资源更新见 [多模式 PE 计算基线](多模式PE与16x16分块计算基线.md)。当前 T05 生产调度器仍为按 kind 配置的独立 test stub 池；T06 已交付共享多模式 PE 的架构设计、内部 task 契约与独立可执行时序/资源原型（见 [Panel-LU 架构设计](Panel-LU架构设计.md)），但尚未接入 T05 `CommandDevice`，正式迁移属 T07。

## 2. 软件侧模块

### 2.1 Input and numeric preprocessing

读取稀疏方阵和 RHS，保留原始数值矩阵 `A`、`b`，不把非对称矩阵数值对称化。Host 数值
预处理是正式模块，独立于 golden checker：

- 二的幂行均衡 `D_r`（记录缩放 exponent）；
- 全局一对一加权 max-product 行匹配 `P_match`：max-product 完美匹配以严格等价的
  sum-of-log 目标求解，调用 SciPy 稀疏 LAPJVsp 分配求解器；不是 MC64 的重新实现，
  也不使用逐列贪心最大值；
- 匹配不完整 → 诊断失败，不产出任何 artifact。

变换（gather 约定 `y[i] = x[p[i]]`）：

```text
B     = P_match · D_r · A
A_hat = Qᵀ · B · Q
b_hat = Qᵀ · P_match · D_r · b
x     = Q · x_hat
```

符号包络按 `pattern(B) ∪ pattern(Bᵀ)` 重算，其后 ordering、fill、etree、supernode、
front 和映射全部重算。residual 与 backward error 一律针对原始 `A x = b` 计算；原始
`A`、`b` 保留给独立 checker；FP64 参考数据不进入设备内存镜像。

### 2.2 Symbolic compiler

负责：

- 构造对称符号包络 `pattern(B) ∪ pattern(Bᵀ)`；
- ordering；
- fill 和 elimination forest；
- supernode、front 和 update 区域；
- local row/column map；
- front 上限和 buffer 需求检查。

该模块不下沉到硬件。硬件只接收已经编译好的结构产物。

### 2.3 Command compiler

将软件内部的 node compiler IR、消除树和 front 描述转换为：

- command ring；
- descriptor table；
- data image；
- completion 预期和依赖 token。

产物为 Command/Descriptor schema v2（manifest `abi.version = 2`，见
[../interface/Command_Schema_v2.md](../interface/Command_Schema_v2.md)）。历史 `NodeTask`
已归档；当前软件内部使用不带设备二进制布局的 node compiler IR。

## 3. 设备侧模块

### 3.1 Command Fetch

从 command ring 读取固定格式命令，检查 manifest `abi.version`、记录大小、ID 和
descriptor 引用，拒绝 v1 记录与非法策略编码，生成非法命令状态。

### 3.2 GCU

GCU 是命令执行器，不负责 ordering、fill 或 supernode 构造。职责包括：

- command decode；
- dependency token 管理；
- buffer 和资源分配；
- Panel、TRSM、GEMM、DMA 的发射；
- timeout、abort 和 completion；
- cycle、bytes、pivot、overflow 和 retry 统计。

### 3.3 Buffer/DMA/Assembly

- 将 DDR 中的 contribution、front 和 descriptor 搬入片上 buffer；
- 管理 front、update、factor 和 scratchpad 生命周期；
- 执行 extend-add；
- 将结果按 descriptor 写回 DDR；
- 将满/空、端口冲突和反压传递给 GCU。

Assembly 可以使用 C++ 容器实现 buffer，但不能直接绕过 DDR/descriptor 从黄金对象读取结果。

### 3.4 HPU

HPU 是 DYNAMIC_PANEL 的主元搜索单元：输入当前 pivot block 内候选行（第 k 步为
`k .. pivot_dim-1`）的候选值和逻辑行号，输出确定性的 pivot 行（最大绝对值，tie-break
取最小逻辑行号）、pivot 值和状态。STATIC 默认路径在运行时旁路 HPU；不同时实现 CALU、
阈值搜索和复杂 tournament 分支。

### 3.5 ATU

ATU 同样只服务 DYNAMIC_PANEL，维护 logical row 到 physical row 的 P-vector 映射；
STATIC 路径在运行时旁路 ATU。pivot 行交换只交换 P-vector 项，计算核的所有访问都通过
同一映射语义进行查询。该 P-vector 是设备局部置换，与 host 预处理映射 `P_match`/`Q` 无关。

### 3.6 Panel-LU

先独立扫描装配完成的全 front 并锁存尺度，再由 Panel controller 分解 A11 的 16×16 tile 任务，复用共享 PE 上的 LU_DIAG、左右 TRSM 和 GEMM_UPDATE 模式；对外仍只修改 A11。
在 SystemC 中显式建模输入就绪、执行、写回、完成和错误事件，PE 内部可采用任务粒度时延，
使用 FP32/FP64 行为运算，并对每个状态配置资源数量和延迟。执行语义由节点 `FRONT_DESC`
的 `pivot_policy`、阈值和 `pivot_dim` 决定：STATIC 写显式 identity P-vector，
DYNAMIC_PANEL 写 pivot block 内的实际交换结果。

### 3.7 TRSM

支持两类分解内操作：

- `TRSM_LEFT_LOWER`：计算 `U12 = L11⁻¹(PF12)`；
- `TRSM_RIGHT_UPPER`：计算 `L21 = F21U11⁻¹`。

最终 solve 复用相同的三角求解语义，在 SystemC 中完成树形前代和回代。RTL solve 不是首版必要条件。

### 3.8 GEMM-Schur

计算：

```text
F22 ← F22 − L21 × U12
```

SystemC 默认可以使用 FP32/FP64 GEMM 行为模型。若使用 INT32 GEMM 后端，量化和反量化只发生在该次 GEMM 的 tile 边界。

### 3.9 Solve Controller

根据已经写回并提交的 L/U/P 和 RHS 执行树形前代、回代。单 RHS 的求解依赖强、计算量相对小，因此首版主要在 SystemC/Host 完成，避免为了完整性新增复杂 RTL 向量核。

## 4. 数据和控制原则

### 4.1 控制与数据解耦

命令表达“做什么”，descriptor 表达“对哪一块数据、以什么尺寸和布局做”。GCU 不读取软件内部的消除树字段。

### 4.2 数值与控制解耦

数值误差不会改变结构依赖。若量化导致 pivot 不稳定，设备返回数值状态，由软件选择重试或报告不支持；不能通过改变 token 语义掩盖失败。

### 4.3 设备路径与黄金路径解耦

所有设备算子只能消费 DDR/descriptor/buffer；FP64 reference 只能在设备输出之后进行检查。

### 4.4 运行时旁路与综合时裁剪

STATIC 路径在运行时旁路 HPU/ATU 的动态映射事务，这是协议层能力；把 HPU/ATU 从设计中
裁剪掉是综合时能力。两者互不等价：旁路不改变设备声明的能力集合，裁剪后设备只能对
`DYNAMIC_PANEL` 返回 `POLICY_NOT_SUPPORTED`。

## 5. 推荐运行模式

```text
FP64_GOLDEN
    数学参考，不模拟设备

FP32_SYSTEMC
    浮点数值 + SystemC 硬件数据流/周期

FP32_SYSTEMC_INT32_GEMM
    浮点系统 + 局部量化 + SystemC INT32 GEMM 行为模型
```

未来获得 Verilog GEMM 后，用同一 transaction 接口替换最后一种模式中的 GEMM backend。
