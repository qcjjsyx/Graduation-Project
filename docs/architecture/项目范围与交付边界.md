# 项目范围与交付边界

状态：当前主线文档

## 1. 项目目标

本项目研究面向稀疏方阵求解的多前沿软硬件协同架构。软件负责把全局稀疏结构编译为消除树、supernode、front、映射和执行命令；设备侧负责按照命令执行节点内的局部数值计算、数据搬运和依赖控制。

正式求解对象是：

```text
Ax = b
```

显式求逆不作为主工作负载。若需要 `A^-1`，可将单位矩阵的多列作为多个 RHS，复用同一套因子和求解流程。

## 2. 数学支持域

### 2.1 支持对象

- 方形稀疏矩阵；
- 数值矩阵可以对称，也可以非对称；
- Host 数值预处理属于支持域：二的幂行均衡 `D_r` + 全局一对一加权 max-product 行匹配
  `P_match`（sum-of-log 目标，SciPy 稀疏 LAPJVsp 分配求解器；非 MC64 重实现，非逐列
  贪心）；匹配不完整即诊断失败，不产出 artifact；
- 符号分析使用预处理后的包络：

```text
B = P_match · D_r · A
S = pattern(B) ∪ pattern(Bᵀ)
```

- 分解在预处理后的系统上进行（`A_hat = Qᵀ B Q`，`b_hat = Qᵀ P_match D_r b`，`x = Q x_hat`）；
  residual 与 backward error 一律针对原始 `A x = b` 计算，原始 `A`、`b` 保留给独立 checker；
- 使用保守的对称符号包络构造 fill、消除森林、supernode 和 front；
- front、panel、tile、候选主元数量存在明确的硬件上限。

### 2.2 不承诺的数学能力

首版不承诺：

- 完整一般非对称 multifrontal LU；
- delayed pivot 和动态 front 扩张；
- update 行参与 pivot 的任意置换；
- 2×2 pivot、完整 MC64 级行列匹配/缩放和独立行列 ordering（host 侧交付的是一对一
  max-product 行匹配 + 二的幂行均衡）；
- 对所有非奇异矩阵都保证低精度路径成功；
- 任意规模的 front 或任意数量的 RHS。

数值失败必须显式报告，不得伪装成控制成功：

- STATIC 固定顺序产生零主元 → `STATIC_PIVOT_FAILURE`，这**不是**矩阵奇异性的结论；
- 实际主元非零但过小 → `PIVOT_UNSTABLE`；出现 NaN/Inf → `NON_FINITE_VALUE`；
- DYNAMIC_PANEL 在当前 pivot block 内找不到可容许主元 → `PIVOT_NOT_FOUND`；
- executor 未实现所声明策略 → `POLICY_NOT_SUPPORTED`（未实现/未支持）。

不静默替换微小主元、不在运行途中切换策略、失败命令不发布 READY token；host 重试从
原始输入或完整重建的状态开始。

## 3. 三层实现边界

```text
FP64 C++ reference
    ↓ 验证数学正确性
FP32/FP64 SystemC architecture model
    ↓ 验证硬件数据流、时序、依赖和资源
Selected RTL prototypes
    ↓ 验证关键接口和局部硬件状态机
```

### 3.1 FP64 C++ 黄金参考

FP64 C++ 路径只负责：

- dense panel LU、TRSM、GEMM/Schur 和 solve 的数学参考；
- 生成可信 pivot、L/U/P 和 solution 对照；
- 计算 residual、backward error 和解误差（对原始 `A x = b`）；
- 作为 SystemC 输出的 checker。

黄金参考不得向设备路径注入 front、pivot、因子或修正后的结果。参考侧显式表达主元策略
语义（STATIC / DYNAMIC_PANEL）；其中经典通用稠密部分主元 API 保留完整数学能力，不是
设备契约。

### 3.2 SystemC 架构模型

SystemC 是项目的主硬件模型，必须覆盖：

- command fetch 和 descriptor 解码（Command/Descriptor schema v2）；
- GCU 调度、依赖 token 和完成状态；
- DDR/DMA 事务、片上 buffer 和生命周期；
- front 装配和 update 写回；
- HPU 主元候选归约（DYNAMIC_PANEL 单元）；
- ATU P-vector 地址映射（DYNAMIC_PANEL 单元）；
- Panel-LU、TRSM、GEMM/Schur 和 solve；
- ready/valid、反压、资源占用和周期统计。

SystemC 的数值设备路径以 FP32/FP64 为主。INT32 只在 GEMM 调用边界作为可选混合精度后端。
主元策略（STATIC 默认 / DYNAMIC_PANEL 可选）当前以契约 + 参考行为交付，设备执行
DYNAMIC_PANEL 未实现。

### 3.3 RTL 原型

RTL 优先覆盖：

- GCU 命令和依赖控制；
- HPU；
- ATU；
- 片上 buffer/SRAM 风格接口；
- 现有或未来的 INT32 GEMM 接口；
- 局部 quantize/dequantize 适配器。

没有 INT32 GEMM RTL 时，使用同一接口的 SystemC `Int32GemmBehavioral` 模块。不能因此暂停整个项目，也不能将 SystemC 行为模型称为 Verilog 验证。

## 4. 六个月交付定义

“完成硬件侧核心模块”在本项目中定义为：

1. SystemC 中所有核心模块都经过显式数据接口和状态机运行；
2. SystemC 完成从命令流、front 装配、分解、写回到求解的闭环；
3. GCU、HPU、ATU 和存储接口形成可运行 RTL 原型；
4. Panel-LU/TRSM 在 SystemC 中完成真实数据通路和周期模型；
5. INT32 GEMM 通过局部量化适配接入 SystemC；
6. 若时间允许，INT32 GEMM 或 quantizer/dequantizer 替换为 RTL；
7. 所有结果区分 FP64 参考、SystemC 设备模型和 RTL/行为后端。

这不是流片级实现，不包含真实 DDR PHY、PCIe、通用 FPGA 驱动和极致吞吐优化。

## 5. 最低验收标准

- 软件产物可被命令解释器读取；
- 单节点和多节点 front 分解正确；
- HPU pivot 和 ATU P-vector 行为可复现（DYNAMIC_PANEL 路径）；
- SystemC 不通过黄金数据旁路完成设备计算；
- FP32 SystemC 能完成端到端 `A x = b` 验证；
- INT32 GEMM 行为后端能报告量化误差、溢出和转换开销；
- GCU/HPU/ATU 的 RTL 原型可以独立测试；
- 所有数值失败都有明确状态和可追踪日志。

## 6. 当前交付范围

### 6.1 已交付（in scope，完成）

- Host 数值预处理：二的幂行均衡 + 全局一对一加权 max-product 行匹配（SciPy 稀疏
  LAPJVsp）；匹配不完整即诊断失败、不产出 artifact；
- Command/Descriptor schema v2 编译产物（manifest `abi.version = 2`，记录大小不变：
  command 32B / descriptor 64B / completion 64B）；
- STATIC 默认主元策略的完整契约表达（`FRONT_DESC` 显式声明、失败状态码、P-vector
  语义）与 host/C++ FP64 参考行为。

### 6.2 在范围内但仅契约/参考级

- DYNAMIC_PANEL 可选策略：契约表达 + 参考行为（pivot 搜索限于 pivot block 内，
  tie-break 取最小逻辑行号）；设备执行未实现，跨 pivot block 需求显式失败
  （`PIVOT_NOT_FOUND`）；
- 主元失败状态码：`STATIC_PIVOT_FAILURE`（非奇异性结论）、`PIVOT_UNSTABLE`、
  `NON_FINITE_VALUE`、`PIVOT_NOT_FOUND`、`POLICY_NOT_SUPPORTED`；
- 运行时旁路与综合时裁剪是两种不同能力：STATIC 在运行时旁路 HPU/ATU 动态映射路径；
  把 HPU/ATU 裁剪出设计是综合时能力，裁剪后设备对 `DYNAMIC_PANEL` 返回
  `POLICY_NOT_SUPPORTED`。

### 6.3 不在已完成范围（out of completed scope）

- SystemC Command executor / 数据面 / 控制面（T04/T05）、DMA、descriptor reader、
  token scoreboard 运行时；
- FP32 数值闭环；
- 局部 INT32/BFP GEMM（其对静态主元的影响需后续重新评估）；
- RTL closure；
- delayed pivot、update 行提升为 pivot、动态 front 扩张（始终不支持）。

### 6.4 当前验证证据

- Python 单元测试 107 passed（`graduation-code/software`，`.venv` python）；
- mypy clean：command_codec / pipeline / matching / command_compiler / manifest /
  front_reference / config；
- C++ CTest 3/3；sanitizer CTest 3/3；
- compile smoke（matching=weighted_matching + STATIC）：
  - 256X256JJ：69 nodes，max front 75，818 commands，1582 descriptors，image
    1,472,984 bytes；host-reference residual 1.56e-10 / backward error 6.65e-14；
  - 576X576JJ：134 nodes，max front 166，1598 commands，3077 descriptors，image
    10,356,400 bytes；residual 1.00e-7 / backward error 3.77e-12；
  - 1024X1024JJ：被现有容量上限拒绝（node 190 front size 264 > max_front_size 256），
    如实报告、不静默放宽；显式提高 `--max-front-size 300` 后编译为 212 nodes，max
    front 298，2534 commands，4871 descriptors，image 21,957,072 bytes；residual
    1.23e-5 / backward error 8.3e-15；
- 字节级可复现性已复核。

以上证据仅覆盖 FP64 验证：FP32 静态设备路径的数值稳定性未完全验证。不得作出任何
硬件加速结论。
