## 2. 总体目标

六个月内形成一条可运行、可验证、边界清晰的软硬件协同闭环：

```text
稀疏矩阵 A、RHS b
  → 软件符号分析/重排/消去森林/supernode/front
  → command stream + descriptor table + data image
  → SystemC Command Fetch/GCU/依赖/buffer/DDR
  → front 装配
  → Panel-LU + HPU/ATU
  → TRSM
  → GEMM-Schur
       ├─ FP32/FP64 行为后端
       └─ 局部 INT32 GEMM 行为后端
  → L/U/P/update 写回
  → SystemC 前代/回代
  → FP64 checker 和统一实验报告
```

最终交付不是完整流片级浮点 LU，也不是任意规模通用非对称 multifrontal 求解器。必须完成的是：

- 软件可以生成稳定、可校验的结构产物和命令流；
- SystemC 可以通过显式命令、descriptor、buffer 和 memory interface 完成单节点及多节点流程；
- FP64 C++ 是独立数学参考，不冒充硬件周期；
- FP32/FP64 SystemC 是主硬件架构模型；
- INT32 只在 GEMM 调用边界量化和反量化；
- HPU、ATU、GCU/存储控制等关键模块有可独立验证的 RTL 原型；
- 所有数值失败、溢出、饱和、pivot 问题和控制失败都可追踪。

## 4. 所有任务的共同工作规则

### 4.1 coding agent 开始前必须做的事

1. 阅读本文件对应任务、当前主线架构文档和目标目录现有代码。
2. 运行一次当前相关测试，记录基线结果。
3. 先说明将修改哪些文件、保留哪些兼容行为、不会修改哪些目录。
4. 如果遇到未冻结的 Panel-LU/TRSM 微架构选择，停止扩大实现范围，先产出设计决策记录。

### 4.2 每个任务的标准交付物

- 源代码或设计文档；
- 自动化测试；
- 至少一个可复现运行命令；
- 运行输出或摘要结果；
- 修改文件列表；
- 已知限制和未完成项；
- 对后续任务的接口影响说明。

### 4.3 必须遵守的限制

- 不读取或写入 `reference_front_f64`、黄金因子或预先计算的 solution 来替代设备路径。
- 不把 `status=OK` 当作数值正确；必须同时报告 residual、backward error、解误差和数值状态。
- 不把 SystemC 行为模型称为 RTL 验证。
- 不将 INT32 scale 扩散为整棵消除树的全局格式。
- 不重新引入 `NodeTask`；设备可见字段进入 descriptor 或 status。
- 不为了通过测试静默吞掉 overflow、saturation、pivot failure 或 dependency error。
- 不修改历史优化分支来“同步当前实现”。当前主线需要时，提取最小逻辑并重新实现。

### 4.4 coding agent 的完成汇报格式

每个任务结束时，要求 agent 按以下结构返回：

```text
任务：Txx
完成内容：
修改文件：

```

## T01：Command、Descriptor 和 Status 契约冻结

### 目标

将软硬件长期交互物固定为版本化 command stream + descriptor table。ABI v2 已完成阶段性验证并归档，不再作为当前输入。

### 依赖

T00。

### 参考文档

[Command Stream 与 Descriptor 接口](interface/Command_Stream_and_Descriptor.md)。

### 实现要求

1. 按 [Command / Descriptor 固定格式 v1](interface/Command_Schema_v1.md) 冻结 little-endian、32B command、64B descriptor、64B completion、command ID、node ID、descriptor ID 和 wait/signal token 语义。
2. 本版本不在 command record 中携带 `schema_version` 或 `record_bytes`，也不在 descriptor record 中携带 `version`；固定长度和字段语义由本规范及 manifest 区域信息确定。
3. 冻结第一批宏指令：

   ```text
   NODE_BEGIN
   LOAD_FRONT
   ASSEMBLE_EXTEND_ADD
   PANEL_LU
   TRSM_LEFT
   TRSM_RIGHT
   GEMM_SCHUR
   STORE_FACTOR
   STORE_UPDATE
   SOLVE_FORWARD
   SOLVE_BACKWARD
   NODE_COMMIT
   ABORT_NODE
   ```

4. 定义 `REGION_DESC`、`FrontDesc`、`ContributionDesc`、`FactorDesc`、`KernelDesc`、`SolveDesc`、`ScaleDesc`、`DependencyDesc` 和 completion record 的最小字段。
5. 明确 descriptor 只描述数据位置、尺寸、stride、布局和局部 scale，不描述软件内部消除树对象。
6. 冻结控制错误和数值错误的区分：`BAD_COMMAND`、`BAD_DESCRIPTOR`、`ADDRESS_FAULT`、`DEPENDENCY_FAILED`、`PIVOT_NOT_FOUND`、`PIVOT_UNSTABLE`、`NUMERIC_OVERFLOW`、`QUANTIZATION_SATURATION`、`PRECISION_RETRY`、`TIMEOUT` 等。
7. 提供 Python 和 C++ 至少一方可读取、校验和打印命令/descriptor 的实现；最好两方共享 golden binary fixture。

### 验收标准

- 相同输入多次生成的 command/descriptor 字节完全一致；
- 截断、版本错误、长度错误、非法 descriptor 引用和 token 错误能够被拒绝；
- command/descriptor 不依赖历史 `NodeTask`；
- 有至少一个单节点和一个父子节点 command fixture。

### 不做

- 不在此任务决定 Panel-LU 内部每个微操作的最终 bit layout；
- 不实现 SystemC GCU；
- 不实现真实 RTL parser。

## T02：FP64 Golden 参考与测试夹具

### 目标

建立独立于设备路径的数学参考，统一给 Panel-LU、TRSM、GEMM、solve 和整树验证使用。

### 依赖

T00。

### 修改范围

优先放在 `graduation-code/systemc` 的独立 reference 目录或共享 C++ library；不得把黄金函数混入设备 module 的状态机。

### 实现要求

1. 实现或整理 dense Panel-LU、partial pivoting、L/U 分块、TRSM、GEMM-Schur 和 residual 计算。
2. HPU 选择规则和黄金参考保持一致：最大绝对值优先，相同值使用确定性 tie-break。
3. 提供 1×1、2×2、4×4、含行交换、近奇异、结构非对称和多 front 小树 fixture。
4. 对每个 fixture 保存输入、期望 pivot、L/U、P-vector、Schur update 和 solution，或保存可重算的 JSON/二进制结果。
5. 统一计算 relative residual、componentwise backward error、relative solution error、minimum pivot ratio 和 pivot growth。

### 验收标准

- 参考函数不依赖 SystemC `sc_start`；
- 参考函数不读取设备 memory image；
- Panel-LU/TRSM/GEMM/Solve 都有单元测试；
- 可用同一份 fixture 检查后续 SystemC 输出。

### 不做

- 不把 FP64 参考结果写入设备 memory 作为运行时输入；
- 不把黄金 pivot 注入 SystemC；
- 不做高性能 BLAS 优化。

## T03：软件 Command Compiler

### 目标

将当前软件生成的消除树、front 和 map 编译为 command batch、descriptor table 和设备可见数据区。

### 依赖

T01；可并行参考当前软件 pipeline。

### 修改范围

- `graduation-code/software/src/pipeline.py`
- `graduation-code/software/src/verify/manifest.py`
- `graduation-code/software/src/memory/`
- `graduation-code/software/src/scheduler/`
- 新增 command/descriptor serializer 和测试

### 实现要求

1. 保留当前排序、fill、消除森林、supernode、front、map 和数据打包逻辑。
2. 以 node compiler IR 作为内部中间结构，将每个节点编译为宏命令序列，不允许 SystemC 重新推导消除树。
3. 为每个 command 建立 descriptor 引用、wait token、signal token 和预期 completion。
4. 生成 command region、descriptor region、data region 和 status region 的地址布局，检查不重叠和对齐。
5. 只生成 Command v1 artifact；历史 ABI v2 实现移动到归档目录，不参与当前构建和测试。
6. 对损坏矩阵、空 RHS、重复 node ID、循环 parent、超出 front 上限和地址溢出给出明确错误。

### 验收标准

- 软件可生成完整 Command v1 artifact；
- command 顺序和 token 能表达完整的 child→parent 依赖；
- 生成结果可被 T01 的 decoder 重新读取；
- 当前主线 software pytest 全部通过，并新增 command compiler 测试；
- 同一输入、配置和 seed 的产物字节稳定。

### 不做

- 不在软件中实现 Panel-LU、TRSM 或 GEMM 数值计算；
- 不把 FP64 参考结果塞进 command/data 区供设备读取；
- 不重新引入旧 `NodeTask` 字段来表达新算子。

## T04：SystemC Memory、Descriptor 和 Buffer 基础设施

### 目标

将 SystemC 从“模块直接访问全局 C++ 容器”改为“通过设备 memory、descriptor 和片上 buffer 访问数据”。

### 依赖

T01、T03。

### 修改范围

- `graduation-code/systemc/include/system_memory.hpp`
- `graduation-code/systemc/include/artifact.hpp`
- `graduation-code/systemc/include/model_types.hpp`
- 新增 memory request/response、descriptor reader、buffer handle 或等价模块

### 实现要求

1. 统一 DDR 地址为 memory image 内的字节地址，禁止使用 Host 指针作为设备地址。
2. 提供可记录的 read/write transaction：地址、字节数、发起 cycle、完成 cycle、状态。
3. BufferManager 必须体现容量、所有权、空闲/装载/计算/写回/释放状态和满/空反压。
4. descriptor 读取必须经过版本、范围、对齐和尺寸校验。
5. front、contribution、factor、update、RHS、solution 和 status 区域必须可独立追踪。
6. 实现独立的 Command v1 artifact loader；不得从归档目录调用旧 ABI v2 loader。

### 验收标准

- memory transaction 测试覆盖正常读写、越界、未对齐、重叠和延迟；
- buffer 测试覆盖双 buffer、满、空、重复释放和错误 owner；
- 设备算子可以通过 buffer handle 读写一块 tile；
- 测试中不能通过 reference front 旁路得到输出。

### 不做

- 不在此任务实现数值 kernel；
- 不模拟真实 DDR PHY/AXI PHY；
- 不引入全局 Tile BFP 量化。

## T05：SystemC Command Fetch、GCU 和依赖执行器

### 目标

让 SystemC 真正按照 command stream 执行，而不是按照 `std::vector<NodeTask>` 直接驱动固定流程。

### 依赖

T01、T04。

### 修改范围

- `graduation-code/systemc/include/full_system.hpp`
- `graduation-code/systemc/src/system_sim.cpp`
- `graduation-code/systemc/include/model_types.hpp`
- 新增 CommandFetch/GCU/scoreboard/resource scheduler

### 实现要求

1. CommandFetch 从 command region 按固定 32B 记录读取命令，检查 ID、flags 和 descriptor 引用。
2. GCU 维护 wait/signal token，并在依赖满足后发射命令。
3. 资源调度至少区分 front buffer、Panel unit、TRSM unit、GEMM unit、DMA/DDR 端口。
4. 支持 command ready/valid、下游 busy、buffer 满和 command ring 截断。
5. 每条命令产生 completion record，包含 command/node/status/cycle/bytes/stall/retry。
6. GCU 直接消费 Command v1，不设置 NodeTask adapter。
7. 可参考归档中 `TaskFetch`、`DependencyScoreboard`、`BufferManager` 的行为，但当前实现不得依赖其旧类型。

### 验收标准

- 单节点 command 可以执行到 `NODE_COMMIT`；
- 子节点完成前，父节点的 `ASSEMBLE_EXTEND_ADD` 不会发射；
- 任意合法的 ready 顺序不会破坏 token 语义；
- command 错误和数值错误分别上报；
- timeline 能显示 fetch、wait、issue、stall、complete 和 commit。

### 不做

- 不在此任务实现 Panel-LU/TRSM/GEMM 内部数值计算；
- 不加入 lookahead 等复杂优化；
- 不把 command executor 直接绑定到某一个 tile size。

## T06：HPU/ATU SystemC 行为和 RTL 契约统一

### 目标

冻结并实现主元选择和逻辑行映射的共同语义，使 SystemC 和 RTL 在边界行为上可对照。

### 依赖

T01、T04；可与 T05 部分并行。

### 实现要求

#### HPU

1. 输入采用 candidate stream：`valid/ready/value/logical_row/last`。
2. 只实现首版最大绝对值归约和固定 tie-break。
3. 输出 `pivot_valid/pivot_ready/pivot_row/pivot_value/fail`，明确空候选、超过最大候选数和 pivot 不稳定状态。
4. SystemC 必须体现收集、归约和输出等待延迟，不得只在一个函数调用中完成全部行为。
5. RTL `hpu_top.sv`、比较树和 testbench 使用同一套边界语义。

#### ATU

1. 维护 `logical_row → physical_row` P-vector。
2. query、swap、init 都使用握手和明确的完成周期。
3. 行交换只修改映射，不搬移 front 数据。
4. Panel、TRSM 和写回访问都必须使用同一个映射语义。
5. 覆盖非法行号、重复 swap、reset 中访问和初始化未完成访问。

### 验收标准

- SystemC/RTL 在相同 candidate、swap、reset 序列上输出一致；
- HPU 覆盖 tie-break、空输入、最大候选数和 backpressure；
- ATU 覆盖 identity、任意 swap、连续 swap、query latency 和非法访问；
- 不支持 delayed pivot、rook、2×2 pivot 时必须返回明确未支持状态。

### 不做

- 不实现复杂 CALU/rook/threshold pivot；
- 不实现动态 front 扩展；
- 不把 HPU 的结果通过黄金参考覆盖。

## T07：Panel-LU 架构说明书（先讨论，暂不追求完整代码）

### 目标

在实现 Panel-LU 之前，形成一份最小但可执行的硬件架构设计。该任务的主要产物是设计文档、接口和待决策项，不要求一次完成 RTL 数值核。

### 依赖

T02、T04、T06；T01 的 `PANEL_LU`/`KernelDesc` 语义已冻结。

### 当前建议的算法边界

对一个 front 按 pivot 区和 update 区划分：

```text
F = [ A11  A12 ]
    [ A21  A22 ]

A11 = L11 U11
A12 = L11 U12
A21 = L21 U11
A22 ← A22 - L21 U12
```

首版只承诺当前 front 内的 partial pivoting、P-vector swap 和 right-looking blocked LU；不承诺 delayed pivot、动态 front 扩展、2×2 pivot 或任意非对称稳定性保证。

### 设计说明必须回答

1. front/panel/tile 在 scratchpad 中的布局和 leading dimension；
2. HPU candidate stream 如何产生，候选范围是 `k..m-1` 还是其他范围；
3. pivot 返回后 ATU swap、数据访问和下一状态如何同步；
4. L 乘子的 reciprocal/divide 如何实现：直接 divider、reciprocal + multiply，还是可配置延迟的行为资源；
5. Panel update 使用多少 MAC/vector lane，是否原地更新；
6. U12/L21 的生成与 TRSM 的边界如何划分；
7. `PIVOT_NOT_FOUND`、`PIVOT_UNSTABLE`、`NUMERIC_OVERFLOW` 如何返回 GCU；
8. 每个状态的 request/response、busy、done、stall 和周期估计；
9. FP32/FP64 SystemC 后端如何共享同一控制状态；
10. 未来 Panel-LU RTL 若不实现，哪些接口仍必须保持稳定。

### 必须产出

- `docs/architecture/Panel-LU架构设计.md` 或等价文档；
- 状态机图或状态表：`IDLE → LOAD → PIVOT_CANDIDATE → PIVOT_SELECT → ROW_SWAP → DIVIDE/RECIPROCAL → PANEL_UPDATE → WRITEBACK → DONE/ERROR`；
- Panel-LU request/response 结构；
- 至少 1 个小 front 的 cycle/transaction trace；
- 未决选项、推荐选项和暂不实现项清单。

### 验收标准

设计可以被 T08 直接实现，不依赖“先写代码再临时决定接口”。所有未决选择必须显式记录，不能伪装成已经冻结。

### 不做

- 不在此任务实现完整 Panel-LU RTL；
- 不提前把 divider、阵列规模或 lane 数写死为最终论文结论；
- 不引入全局 INT32/BFP 计算路径。

## T08：Panel-LU SystemC Engine

### 目标

根据 T07 的架构说明，将 Panel-LU 从普通 C++ 一次性函数调用改为显式 buffer 驱动、状态推进和可观测周期的 SystemC 设备模块。

### 依赖

T02、T04、T05、T06、T07 已通过评审。

### 实现要求

1. 只从 front descriptor/scratchpad 读取输入，禁止读取黄金 front。
2. 显式实现 load、candidate、pivot select、row swap、divide/reciprocal、panel update、writeback、done/error。
3. 每个状态有明确的启动条件、完成条件、延迟、反压和异常出口。
4. HPU 和 ATU 通过 transaction 接口连接，不在 Panel-LU 内复制另一套 P-vector 或 pivot 逻辑。
5. 支持 FP32/FP64 行为数值后端；精度只影响数值运算，不改变 command/token 语义。
6. 对单列、tail tile、pivot 行交换、近零 pivot、overflow 和 buffer 满进行记录。
7. 生成 panel trace：状态、k、pivot 行、swap、计算 tile、bytes、cycle、status。

### 验收标准

- 1×1、2×2 行交换、4×4 blocked panel 与 T02 golden 结果一致；
- 与旧 C++ kernel 的结果差异在配置阈值内，但设备路径不调用旧 kernel 直接写结果；
- backpressure 会导致等待而不是丢数据；
- 失败节点返回明确状态并被 GCU 记录；
- CTest 包含正常、边界和失败用例。

### 不做

- 不实现 Panel-LU 的完整 RTL 数值核；
- 不实现 delayed pivot 和动态 front；
- 不为了通过高条件数矩阵而自动读取 FP64 reference rescue。

## T09：TRSM 架构说明书（先讨论，暂不固化微架构）

### 目标

确定分解内 TRSM 和最终 solve 共用的三角求解语义、数据布局、tile 依赖和资源模型。

### 依赖

T02、T04；可与 T07 并行，但必须在 T10 前完成。

### 首版操作范围

```text
TRSM_LEFT_LOWER   : U12 = L11^-1 · A12
TRSM_RIGHT_UPPER  : L21 = A21 · U11^-1
SOLVE_FORWARD     : L · y = P b
SOLVE_BACKWARD    : U · x = y
```

### 设计说明必须回答

1. 三角矩阵和 RHS tile 的存储布局、stride、in-place/out-of-place 选择；
2. 左解和右解的行/列方向、对角线处理和单位/非单位对角语义；
3. 对角 tile 的内部 solve 与非对角 tile 的 GEMM/MAC 更新如何划分；
4. Panel-LU 生成的 P-vector 如何影响 RHS/factor 访问；
5. `TRSM_LEFT` 与 `TRSM_RIGHT` 如何复用 solve engine；
6. reciprocal/divide、MAC lane、tile buffer 和 dependency scoreboard 的资源需求；
7. 维度不是 tile size 整数倍时的 mask/tail 行为；
8. FP32/FP64 行为模式和周期模型；
9. singular、zero diagonal、unstable diagonal 和 overflow 状态；
10. 首版为什么不要求 TRSM/solve RTL，以及未来可替换的接口边界。

### 必须产出

- `docs/architecture/TRSM架构设计.md` 或等价文档；
- 左/右 TRSM 的伪代码和 tile dependency 图；
- request/response、状态表和周期估算规则；
- 与 Panel-LU、GEMM、Solve Controller 的接口说明；
- 至少 3 个可手算测试案例。

### 验收标准

设计说明必须能够直接指导 T10 的接口和测试编写：左/右 TRSM 的输入输出、依赖、tail、失败状态和周期模型不能留作隐含约定；所有暂未决定的微架构选项必须列入未决清单，并且不能阻塞 SystemC 首版实现。

### 不做

- 不把完整稀疏树形求解直接做成 RTL；
- 不加入完整 BLAS 参数空间、转置组合和复杂 batched 模式；
- 不为了性能提前设计大规模脉动阵列。

## T10：TRSM SystemC Engine

### 目标

按照 T09 实现显式三角依赖、tile 读取、对角处理、更新和写回的 SystemC 模块。

### 依赖

T02、T04、T05、T09；GEMM 接口可以先使用临时 stub，正式结果由 T11 接入。

### 实现要求

1. 支持 `TRSM_LEFT_LOWER` 和 `TRSM_RIGHT_UPPER` 两种模式。
2. 对角 tile 使用明确的 triangular mask 和 diagonal policy。
3. 非对角 tile 的更新通过统一的 GEMM/MAC transaction，不直接改全局 C++ 矩阵。
4. 支持 tail tile、zero diagonal、backpressure、buffer 不足和 writeback 延迟。
5. 记录每个 tile 的 start/end、读写 bytes、stall、数值状态和结果摘要。
6. Solve Controller 后续复用该模块的数学/事务语义，而不是复制另一套三角求解实现。

### 验收标准

- 2×2、4×4、非整 tile 维度和行交换 RHS 案例与 T02 golden 一致；
- 左解和右解都能被单独调用；
- 输入输出 descriptor、stride 和布局校验有效；
- 设备路径不读取 reference factor 或预计算 solution；
- CTest 包含正常和非法对角线用例。

### 不做

- 不实现高吞吐 TRSM RTL；
- 不实现任意转置/共轭转置组合；
- 不把量化 scale 扩散到整棵树。

## T11：FP32 GEMM、Precision Adapter 和 INT32 GEMM 行为模型

### 目标

建立未来可以替换为 RTL 的 GEMM transaction backend，并验证局部 INT32 量化适配的数值和周期代价。

### 依赖

T01、T04；T07/T09 给出 Panel/TRSM 的调用边界后完成集成。

### 实现要求

1. 定义统一 `GemmReq/GemmRsp`，至少包含 command ID、descriptor ID、M/N/K、A/B/C buffer、stride、scale、累加模式和 status。
2. 实现 `GemmFp32Behavioral` 或等价 FP32/FP64 参考设备后端。
3. 实现 `PrecisionAdapter`：tile maxabs/二的幂 scale、round、saturate、overflow、dequantize。
4. 实现 `Int32GemmBehavioral`：INT32×INT32、INT64 或明确 guard-bit 累加、K 维分块、tile latency、写回和反压。
5. 量化只发生在一次 GEMM 调用边界：

   ```text
   FP tile → quantize → INT32 GEMM → dequantize → FP tile
   ```

6. 提供累加宽度、tile size、scale 策略、饱和策略和 latency 配置。
7. 统计输入量化误差、输出误差、overflow、saturation、quantize/dequantize cycles 和 bytes。
8. 明确不实现 FP8 主路径；FP8 只可作为未来独立实验，不得成为当前交付依赖。

### 验收标准

- INT32 行为模型与独立 int64 oracle 一致；
- 测试覆盖正负数、全零、最大值、饱和、K 分块和反压；
- FP32 与局部 INT32 GEMM 的误差可单独报告；
- SystemC 上层只依赖 `GemmReq/GemmRsp`，未来替换 RTL 不需修改 GCU/front 流程；
- 没有把 tile scale 写入整棵树的全局 NodeTask 协议。

### 不做

- 不声称已经完成 INT32 GEMM RTL；
- 不实现全局 BFP front 装配；
- 不实现 FP8 量化器。

## T12：单节点与多节点 SystemC 集成

### 目标

将 T04–T11 的组件连接成真正的节点执行器和消除树执行器。

### 依赖

T03、T05、T06、T08、T10、T11。

### 实现要求

1. 单节点按以下顺序执行：

   ```text
   NODE_BEGIN
   LOAD_FRONT
   ASSEMBLE_EXTEND_ADD
   PANEL_LU
   TRSM_LEFT / TRSM_RIGHT
   GEMM_SCHUR
   STORE_FACTOR / STORE_UPDATE
   NODE_COMMIT
   ```

2. 多节点执行必须从 DDR 读取 child update，并在父节点 commit 后再释放资源。
3. 设备运行时 backend 可选择 `FP32_SYSTEMC` 或 `FP32_SYSTEMC_INT32_GEMM`；`FP64_GOLDEN` 作为独立参考和 checker，不作为设备 command backend。
4. 支持多根 elimination forest、任意合法 child 完成顺序和 buffer 重用。
5. 保留 Command v1 单节点回归，并增加多节点 command artifact 端到端入口。
6. 将所有 command/node/operation/timeline/memory/status 统一写入报告。

### 验收标准

- 单节点闭环通过；
- 两层和三层父子树通过；
- 多根森林通过；
- 随机 child 顺序不会违反依赖；
- parent 在所有 child update ready 前不能进入装配；
- 没有 reference front、预选 pivot 或 Host solve 旁路；
- 控制成功和数值成功分别报告。

### 不做

- 不做 lookahead、复杂并发调度或极致吞吐；
- 不在此任务加入新的数值格式；
- 不把旧 optimization-v1/v2/v3 复制回主线。

## T13：SystemC Solve Controller 和完整 Ax=b 闭环

### 目标

使求解阶段成为明确的 command 执行过程，读取已提交的 L/U/P/RHS，完成前代、回代并把 solution 写回设备数据区。

### 依赖

T02、T05、T10、T12。

### 实现要求

1. 实现 `SOLVE_FORWARD` 和 `SOLVE_BACKWARD` command。
2. 前代使用 P-vector 语义处理 RHS；不得假设物理行等于逻辑行。
3. 回代按消除树和因子 descriptor 读取已经写回的 U/L；不得读取 golden factor。
4. 结果写入 `SOLUTION_DATA`，再由独立 checker 读取计算 residual。
5. 支持单 RHS；多 RHS 只要接口可扩展即可，不作为首版必须性能优化项。
6. 支持 FP32/FP64 SystemC 数值模式；INT32 GEMM 模式仍使用浮点三角 solve 语义。
7. 记录 forward/backward 的 command、tile、bytes、cycles、stall 和 numeric status。

### 验收标准

- 小型稠密/稀疏树与 T02 golden solution 一致；
- 多级树完成 `Ax=b`；
- P-vector 行交换结果正确；
- 因子缺失、zero diagonal、descriptor 错误和 buffer 不足有明确失败状态；
- 最终 residual、backward error、solution error 可复现。

### 不做

- 不实现 solve RTL；
- 不实现显式逆矩阵专用硬件；
- 不使用迭代求精掩盖基础前代/回代错误。迭代求精只能作为后续可选实验。

## T14：RTL 控制、HPU、ATU 和存储接口原型收硬

### 目标

将已有 RTL 子模块从孤立原型推进为共享 command/status/transaction 语义的可验证控制原型。

### 依赖

T01、T05、T06；可与 T12/T13 并行。

### 修改范围

- `graduation-code/hardware/GCU/`
- `graduation-code/hardware/HPU/`
- `graduation-code/hardware/ATU/`
- `graduation-code/hardware/QAU/`

### 实现要求

1. 补齐 `gcu_top.sv` 的最小 command parser、token scoreboard、buffer/resource interface 和 completion/status interface。
2. 将 `gcu_micro_scheduler.sv` 的 F12/F21/Schur 占位逻辑明确为已实现或未实现状态，不能默默跳过。
3. HPU 使用确定的 candidate handshake、tie-break、reset、empty 和 max candidate 行为。
4. ATU 统一 init/query/swap 的 ready/done 语义和 row width。

### 不做

## 6. Panel-LU/TRSM 后续讨论的最小决策清单

在 T07/T09 评审时，优先讨论以下问题。没有结论的项目保持为参数或接口，不由 coding agent 私自固定：

### Panel-LU

- panel 是按列串行、按 tile 串行，还是允许有限 lookahead；
- divider 与 reciprocal + multiply 的资源/延迟选择；
- L/U 是否原地存储，还是使用双 buffer；
- HPU 候选收集与 Panel update 是否共享 buffer 端口；
- pivot 行交换是只改 P-vector，还是需要局部数据重排；
- Panel-LU 与 TRSM 的职责边界；
- 首版最大 front、pivot_dim、candidate 数和 tile 尺寸。

### TRSM

- 左解/右解是否统一为一个参数化 engine；
- 对角 tile solve 与非对角 update 的资源划分；
- MAC lane、divider/reciprocal 和 scratchpad 的最小配置；
- solve 阶段是否复用分解内 TRSM 的命令和数据格式；
- tail tile、单位对角、zero diagonal 和失败状态；
- 首版只做 SystemC，还是为未来 RTL 保留精确 transaction wrapper。

这两组讨论的目标不是一次设计出最终最高性能架构，而是先得到一个能被 SystemC 真实执行、被测试验证、未来可替换为 RTL 的最小架构。

## 9. 结论

后续 coding agent 的核心任务不是把旧代码继续补大，而是沿着以下顺序形成可替换的实现层次：

```text
契约 → 软件编译器 → SystemC 设备基础设施
     → Panel-LU/TRSM/GEMM 算子
     → 单节点/多节点/求解闭环
     → RTL 控制原型
     → 分层验证和实验收口
```

Panel-LU 和 TRSM 在架构评审前只实现说明书和接口，不由 agent 擅自决定最终微架构；INT32 只在 GEMM 边界出现；SystemC 必须逐步从 C++ 数值旁路改为显式 buffer/状态机/事务执行。按照此任务划分推进，才能让每个阶段都有独立成果，并且在某个 RTL 模块受阻时不影响整个项目交付。
