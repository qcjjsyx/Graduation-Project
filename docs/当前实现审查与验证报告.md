## 2. B01：abort 删除待取的立即错误响应，设备批次永久挂起

### 触发、影响与定位

1. 使用合法两层树 artifact，把 cmd 3（TRSM_LEFT）的 descriptor 中 M 改为 2；该 fixture 的 pivot_dim 为 1，因此这是运行期形状错误。
2. artifact loader 接受字节布局；TRSM adapter 正确产生 BAD_DESCRIPTOR 的立即响应，并向控制面报告请求已接受。
3. 在下次控制面 poll 该响应之前，对 node 0 调用 `abort_node(0)`。
4. `TrsmExecutionUnit::abort_txn` 删除 `immediate_`，而该请求从未进入 engine，engine 不可能再产生替代终态。
5. 控制面仍持有 `unit_active`，按“取消后等待在途访问排空，再由终态响应释放资源”的约定等待。cmd 3 永远停在 Running，最终只写出 14/15 条 completion。

直接根因在 [panel_exec_unit.cpp:304](../graduation-code/systemc/src/controlplane/panel_exec_unit.cpp#L304) 的 `TrsmExecutionUnit::abort_txn`：匹配 txn 后执行 `immediate_.reset()`。等待端是 [control_plane.cpp:1914](../graduation-code/systemc/src/controlplane/control_plane.cpp#L1914) 的 `CommandDevice::abort_node`，其中 `unit_active` 分支有明确的终态响应排空约定。错误形状本身被拒绝是正确行为；**拒绝与 abort 相遇后不再终止**才是缺陷。

`PanelExecutionUnit`、`GemmExecutionUnit` 也存在相同的 immediate 清空写法，修复时应一并检查；本报告的完整设备复现针对 TRSM_LEFT，不把未经同样复现的路径列成额外已确认缺陷。

### 最小复现

先按第 5 节构建并运行 CTest，得到 `t11_fixtures/two_level/fp32/device`。把以下源码保存为 `/tmp/grad-review-abort.cpp`，从仓库根目录编译。它只在内存中修改 artifact，不改仓库 fixture。

```cpp
#include <fstream>
#include <iostream>
#include <iterator>
#include "controlplane/control_plane.hpp"
namespace cp=hw::controlplane; namespace dp=hw::dataplane; namespace cmd=hw::command;
int main(int argc,char** argv) {
 if(argc!=2)return 2;
 auto original=dp::load_artifact(argv[1]);
 auto c=cmd::CommandCodec::decode(original.image.data()+original.config.command_table_addr+3*32,32);
 auto address=original.config.descriptor_table_addr+c.descriptor_id*64ull;
 auto d=cmd::DescriptorCodec::decode(original.image.data()+address,64,original.image.size());
 d.body_words[3]=2; // TRSM_LEFT M should be p=1; syntactically valid, runtime BAD_DESCRIPTOR.
 auto bytes=cmd::DescriptorCodec::encode(d);
 std::copy(bytes.begin(),bytes.end(),original.image.begin()+address);
 std::ifstream in(std::string(argv[1])+"/manifest.json");
 std::string manifest{std::istreambuf_iterator<char>(in),{}};
 original=dp::load_artifact_from_bytes(manifest,original.image);
 std::cout<<"loader accepted malformed runtime shape\n";
 for(bool abort:{false,true}) {
  cp::ControlPlaneConfig config; config.enable_real_panel=true; config.backend=cp::ExecBackend::RequireRealKernels;
  cp::CommandDevice device(original,config); std::string error; if(!device.start(&error)){std::cerr<<error;return 3;}
  bool issued=false;
  for(int i=0;i<10000&&!device.finished();++i){
   device.tick();
   if(abort&&!issued&&device.debug_dump().find("cmd 3 node 0 op 5 phase=Running")!=std::string::npos){
    std::cout<<"abort at "<<device.cycle()<<'\n';device.abort_node(0);issued=true;
   }
  }
  std::cout<<"abort="<<abort<<" issued="<<issued<<" state="<<cp::batch_state_name(device.state())<<" completed="<<device.completion_written()<<" cycles="<<device.cycle()<<'\n';
  if(abort) std::cout<<device.debug_dump();
 }
}
```

无 abort 的 completed 表示错误批次正常收尾，不表示错误数值成功。10000 拍是复现保护上限；根据响应已被删除且 engine 无该事务的状态，不存在未来自然完成事件。实际调用 `run(max_cycles)` 时，外层保护会将 batch 置为 timeout fault，因此不表示 CLI 进程必然无限运行；缺陷是事务无法产生终态、不能正常排空收尾。用 sanitizer 库重新链接此复现也得到同样挂起，未出现内存/未定义行为诊断；这是一项生命周期逻辑错误。

### 测试为什么没抓到，以及最小修复建议

当前回归分别覆盖非法 descriptor 和正在真实执行的事务取消，但没有交叉覆盖“adapter 已接受、立即错误响应尚未被控制面取走”的窄窗口。一般执行后再 abort 的测试进入 engine 的排空路径，因此不会丢失终态。

最小修复方向：保留待取的 `immediate_`，将其转为该 txn 的唯一 ABORTED 终态，或者按明确约定保留已确定的错误终态；不能直接删除。保证一次接受恰好对应一次可取终态。对 Panel/TRSM/GEMM adapter 的同类代码统一核查。不要通过无条件提前释放 tracker 来绕过等待，否则真实在途写回可能污染已复用的 front。

应补两层回归：adapter 层 `submit(非法 shape) → abort_txn → poll` 必须返回一次终态且之后为空；设备层上述两层树必须有限拍完成，所有命令完成、front 释放、scratch lease 无残留。**本次未实施修复。**

## 3. B02：HPU 输出 valid 未在握手时清除，结果重复提交

### 根因与影响

[hpu_top.sv:90](../graduation-code/hardware/HPU/hpu_top.sv#L90) 在 OUT 的 `pivot_valid && pivot_ready` 成立后转 IDLE；但 [hpu_top.sv:137](../graduation-code/hardware/HPU/hpu_top.sv#L137) 对应时序分支的 `pivot_valid_r <= 1'b0` 被注释。valid 到后续 IDLE 时序分支才清除，所以两个连续时钟沿都满足 valid/ready。下游按标准 ready/valid 契约会接受两次同一个主元结果，可能重复 swap 或推进控制状态。

### 最小复现与工具边界

Icarus 对原始 `hpu_core_tree.sv` 的 struct-array 展开发生内部 assertion（`elab_expr.cc:2677`，源码触发点约第 54 行），因此本次没有获得完整 HPU 的原样仿真结果。为隔离输出握手，使用下列确定性 core 替身，**被测 hpu_top.sv 保持原样**。替身只提供一个稳定合法结果；该复现证明 top 的协议问题，不证明实际比较树数值逻辑。

保存为 `/tmp/hpu_handshake.sv`：

```systemverilog
// Isolate unchanged hpu_top handshake; avoid Icarus struct-array elaboration bug.
module hpu_core_tree #(parameter DATA_W=32, ROW_IDX_W=8, MAX_ELEMS=256)(
input logic signed [DATA_W-1:0] cand_val[0:MAX_ELEMS-1],
input logic [ROW_IDX_W-1:0] cand_row[0:MAX_ELEMS-1],
input logic [$clog2(MAX_ELEMS):0] num_elems,
output logic [ROW_IDX_W-1:0] pivot_row,
output logic signed [DATA_W-1:0] pivot_value, output logic pivot_valid);
assign pivot_row=0; assign pivot_value=7; assign pivot_valid=(num_elems!=0);
endmodule
module tb;
reg clk=0; always #5 clk=~clk;
reg rst_n=0, pivot_start=0,in_valid=0,in_last=0;
wire pivot_busy,in_ready,pivot_valid,pivot_fail;
wire [7:0] pivot_row; wire [31:0] pivot_value;
integer accepted=0;
hpu_top dut(.clk(clk),.rst_n(rst_n),.pivot_start(pivot_start),.pivot_busy(pivot_busy),
.in_valid(in_valid),.in_ready(in_ready),.in_value(32'd7),.in_row_logical(8'd0),.in_last(in_last),
.pivot_valid(pivot_valid),.pivot_ready(1'b1),.pivot_row(pivot_row),.pivot_value(pivot_value),.pivot_fail(pivot_fail));
always @(posedge clk) if(rst_n && pivot_valid) begin accepted=accepted+1; $display("accepted=%0d time=%0t busy=%b",accepted,$time,pivot_busy); end
initial begin
#12; rst_n=1; @(negedge clk); pivot_start=1; @(negedge clk); pivot_start=0; in_valid=1; in_last=1;
@(negedge clk); in_valid=0; in_last=0;
repeat(6) @(negedge clk);
$display("EXPECTED=1 ACTUAL=%0d",accepted); if(accepted!=1) $fatal(1,"duplicate HPU result handshake"); $finish;
end
endmodule
```

实际输出：`accepted=1 time=55 busy=1`，随后 `accepted=2 time=65 busy=0`，最终 `EXPECTED=1 ACTUAL=2` 并触发 `$fatal`。

原有 top testbench 主要观测首个结果和延迟，没有以“每接受一个请求恰好接受一个输出”为标准累计握手次数。最小修复是在 OUT 握手的时钟沿同步清除 valid，并在 ready=0 时稳定保持结果。应增加 ready 恒 1、随机背压和连续请求的计数断言。**本次未修复；该 RTL 未接入当前 STATIC 主线。**

## 4. B03：ATU 同时接受 cfg 与 pivot，但只执行 pivot

### 根因与影响

[ATU.sv:157](../graduation-code/hardware/ATU/ATU.sv#L157) 的 `pivot_req_ready` 与 [ATU.sv:189](../graduation-code/hardware/ATU/ATU.sv#L189) 的 `cfg_ready` 都仅由 init_state==IDLE 决定。两路同时有效时，双方都看见接受条件成立；但 [ATU.sv:174](../graduation-code/hardware/ATU/ATU.sv#L174) 的时序写口先处理 pivot，cfg 位于 `else if`，没有执行也没有排队。

把不相交的 cfg 写 `map[2]=3` 与 swap(0,1) 放在同一拍，可排除“同地址操作定义先后”的歧义。随后查询 2 仍为 2，说明已接受的写被静默丢弃。模块没有通过 ready 把互斥要求告诉调用方。

### 最小复现

保存为 `/tmp/atu_collision.sv`，原始 ATU 模块不替换：

